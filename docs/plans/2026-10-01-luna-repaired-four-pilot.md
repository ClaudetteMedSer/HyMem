### Findings established by root review and separate GPT-6 Sol cross-check

1. The timed-out call had approximately 119.2 seconds available for events;
   preflight took approximately 0.78 seconds and turn start approximately
   0.0025 seconds. This is not evidence of a startup/preflight budget drain.
2. The last parser-visible event was about 4.08 seconds into the invocation.
   The last raw enqueue/dequeue was about 59.45 seconds in. These are different
   measurements: `_TimedQueue` counts all complete decoded JSON messages,
   including RPC responses and notifications that routing consumes internally.
   Counts are relative to the invocation baseline; earlier queued messages can
   therefore make dequeues exceed new enqueues.
3. The frozen router can validate and consume `thread/started` and retired-thread
   status/closed notices without returning them to the turn parser. Root's
   invented sequence reproduced a late dequeue, unchanged six-event parser
   count, last `item_started`, empty queue and timeout. The actual late message's
   category was not retained, so retired-thread traffic is an explanation that
   fits, not a proven identification of the historical message.
4. Code inspection and negative controls found no demonstrated path that silently
   drops a matching final, usage, `turn/completed` or nonretry error. Early events
   while `turn/start` is pending are preserved. Valid bounded retry notifications
   remain visible; unexpected agent-message deltas fail closed. Missing final or
   usage at completion produces an incomplete-turn failure, not this timeout.
   This agrees with the documented completion lifecycle in the
   [official OpenAI app-server documentation](https://learn.chatgpt.com/docs/app-server).
5. Alive process / running reader / empty queue are a snapshot, not proof of
   upstream health or a deadlock. The current reader blocks in line-oriented
   reading and does not observe partial-frame progress. Provider silence,
   app-server silence and an unfinished stdout line remain indistinguishable.
   There is no evidence-based runtime fix for the underlying timeout yet.

### Proposed narrow repair: observability first, not a timeout workaround

The concrete repairable issue is missing attribution between raw message
receipt, intentional routing and parser consumption. The repair must not be
represented as resolving the underlying live timeout.

1. In a new source-pinned observer version, record finite counters and last
   categories at raw dequeue (before later validation can raise), validated
   routing disposition and parser return. Scope separately to preflight,
   turn-start, event wait and cleanup; reset per invocation. Use fixed enums
   for message family, active/retired/other/unknown thread relation,
   matching/other/unknown turn relation and last item kind. Retain the first
   failure immutably; bounded/saturated counters must be explicit. Keep all
   raw IDs, methods outside the allowlist, payloads, text and credentials out.
2. Add only necessary finite context: current existing runner-stage enum and
   coarse input-size bucket at invocation entry, with per-client/per-call
   ownership safe for four workers. Record raw-versus-returned final/usage/
   completion/error categories without treating observation as parser
   acceptance. No process-global patch for application attribution.
3. Keep no-complete-line evidence distinct from no-provider-progress evidence.
   Merely setting `reader_state=reading` does not distinguish silence from a
   partial line. Any future framing instrumentation needs its own narrow
   proposal, raw-content-free implementation and byte-fragmentation tests;
   it must not be silently folded into a parser replacement.
4. A separate Sol implementation, if approved, should be followed by root
   review and offline controls: late lifecycle traffic; completion/error before
   and after the start-RPC response; delayed final/usage; malformed and unknown
   metadata; counter reset/rotation/saturation; first-failure preservation;
   four-worker cross-contamination; privacy checks. Root must verify unchanged
   answers, parser decisions, deadlines, model/account/quota/usage and cleanup.
5. Only after observer acceptance should a separate versioned runner/reader/
   bundle integration be proposed. Preserve this consumed run and all receipts.
   Any live validation requires an explicit evidence-based purpose and new
   authorization/immutable identity; do not blindly repeat the four questions.

No timeout extension, retry, cap increase, prompt/model change, semantic gate
relaxation or paid API fallback is justified by the current evidence. If new
evidence still shows only an uncompleted active turn, pause rather than describe
instrumentation as a runtime fix or continue rerolling.
